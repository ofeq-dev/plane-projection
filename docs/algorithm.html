Plane projection — the algorithm, visualized

The companion to docs/algorithm.md (requirements: docs/srs.md, FR-12/FR-13) — the same algorithm, the same readable names, and the same numbers as its hand-checked fixtures, playing out pixel by pixel.

In plain words

Think of the input volume as a block of small cubes, where every cube holds one brightness number. A plane from the CSV is a flat triangle- or trapezoid-shaped sheet placed inside (or reaching beyond) that block. For every pixel of the sheet the renderer asks one question: which cube does this pixel sit closest to? That cube's brightness number is copied into the pixel; pixels that miss the sheet, or whose nearest cube lies outside the block, stay black.

Concretely: the sheet's size comes from the plane's corners — one pixel row per voxel-length step down its two slanted edges (the legs), one pixel column per voxel-length step across its base. Each row's two ends slide down those legs, so a triangle's rows widen as you go down while a trapezoid's widen, then stay wide. Each pixel of a row samples half a step to the side of the row's centre, keeping the row symmetric about the middle. Sample points are rounded to the nearest cube — an exact tie goes to the even side — and the cube's value is scaled to a 0..255 gray level over the file's full value range, never stretched to the picture's own brightest value.

Gray levels, not content-stretching

  

    Every cube's number is an integer of a fixed width — 8, 16 or 32 bits, signed or
    unsigned (numpy calls this the array's dtype, "data type"). Gray levels only
    run 0..255, so values are mapped over the type's full span: an unsigned type
    maps 0..its maximum (255 / 65535 / 4294967295) onto 0..255; a signed type maps its
    minimum..maximum (e.g. −32768..32767) onto 0..255. The picture's own brightest value is
    never the scale — a black-ish pixel really is black-ish in the video (FR-12e).
